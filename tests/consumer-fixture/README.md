# Consumer-path fixtures

Committed on purpose. `reusable-security.yml` performs its own `actions/checkout`, so a fixture
generated at runtime by an earlier job does not exist when the reusable workflow runs. Proving the
**consumer path** therefore requires fixtures that are present in the tree.

Two directories, making opposite assertions:

| Directory | Contents | Expected |
|---|---|---|
| `clean/` | current, non-vulnerable pins | gate **passes** — caller succeeds |
| `seeded/` | pins with well-known HIGH/CRITICAL advisories | findings detected and handed to the gate; it **blocks** at any rung above crawl (at crawl, the kit default, they are `PROCEED_WITH_ADVISORY`) |
| `full/` | **generated by `tests/make_fixture.py`** — Python, Node, .NET/C#, Java, Go, C/C++, Terraform, Dockerfile, three Azure/Entra credential classes, and a negative control | gate **blocks** on the generated secrets at every rung — caller fails — and every `EXPECTED_SIGNALS` entry must be detected |

**Where the block happens (lane L-S, owner ruling O-24).** The security gate is the single
enforcement point: scanner jobs -- the secret scan included -- report findings and fail only when
they could not scan, so in the negative run the gate fails (BLOCKED on the seeded secrets) while the
secret scan, Semgrep and Trivy succeed with their findings on record. `consumer-path-test.yml`
asserts exactly that shape. A secret blocks unless the policy register excepts that one finding,
ticketed and attributed (owner ruling 2026-10-22; `docs/adoption/POLICY_REGISTER.md`).

## `full/` carries a signal contract, not just files

`EXPECTED_SIGNALS.json` states what each planted file must produce. `tests/verify_expected_signals.py`
downloads the SARIF the consumer run actually emitted and compares **expected against observed**.

That distinction is the whole point. Counting green jobs proves nothing: a scanner pointed at the
wrong path, handed the wrong config, or quietly writing an empty report is green all day. Two
illusions of exactly that kind shipped here and survived a fully green `validate-scanners` — a
`trivy-action` tag that never existed, and 14 Azure secret rules the reusable workflow never loaded.

`secrets/negative_controls.md` must produce **no** finding. A scanner that fires on documented
near-misses costs more coverage than it buys, because people stop reading it.

**These files contain synthetic credentials on purpose** and are deliberately *not* under
`tests/fixtures/`, which the gitleaks allowlist exempts by path. Allowlisting them would make the
seeded secrets invisible and the test would pass having proven nothing. A repo-wide scan of this kit
will therefore flag them — correctly. Pre-commit hooks may need `--no-verify` for this directory.

## Why dependency vulnerabilities and not secrets

A seeded *secret* would be the obvious choice and is the wrong one here. The gitleaks allowlist
exempts `tests/fixtures/` by path, so a seeded credential placed under a fixture directory is
invisible **by design** — the seeded test would pass while proving nothing. Dependency advisories
carry no such path exemption, so `deps-scan` genuinely has to detect them through the reusable
workflow.

That distinction is the whole point of the consumer-path test: the tool-level probes in
`validate-scanners.yml` prove the *scanners*. Only this proves the **contract** — that `paths`
threads through, that findings survive to the gate, and that the gate blocks the **caller**.

## These pins are deliberately vulnerable

Nothing here is installed, imported, or executed. They exist to be *detected*. Do not "fix" them —
upgrading them silently disables the seeded assertion and the test would go green having tested
nothing. If a pin ever stops producing a HIGH/CRITICAL finding, replace it with one that does and
say so in the commit message.
